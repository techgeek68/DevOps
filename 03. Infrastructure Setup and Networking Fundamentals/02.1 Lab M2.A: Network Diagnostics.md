### Part 2: Understand Your Tools

Work through each tool below before moving on to Part 3. For each one, run the example commands against a known-good target and read the explanation of what the output means. You will rely on this reference throughout the rest of the lab.

#### `ping`

`ping` sends ICMP Echo Request packets to a host and reports whether it responds. It tests basic reachability at Layer 3.

```bash
# Basic ping: send 4 packets and stop
ping -c 4 8.8.8.8

# Ping a hostname (tests DNS resolution + reachability)
ping -c 4 google.com

# Ping with a specific packet size (tests MTU issues)
ping -c 4 -s 1400 8.8.8.8
```

**What the output tells you:**

- `icmp_seq`: sequence number. Gaps indicate dropped packets.
- `ttl`: Time to Live. Lower TTL suggests more hops to the destination.
- `time`: round-trip latency in milliseconds.
- `packet loss`: any percentage above 0% indicates a network problem.

**Diagnostic scenarios:**

- `ping 8.8.8.8` succeeds but `ping google.com` fails: DNS resolution is broken, not connectivity.
- `ping 192.168.1.1` (your gateway) fails: a local network or firewall issue, not an internet issue.
- 100% packet loss: the host is unreachable, a firewall is blocking ICMP, or the host does not exist.

> Some hosts block ICMP even when services on them are perfectly reachable. A failed `ping` does not conclusively prove a host is down. Follow up with `curl` or `telnet` on a specific port.

#### `traceroute`

`traceroute` maps the path packets take from your host to a destination, showing each router hop along the way.

```bash
# Install if not present
sudo dnf install -y traceroute

# Basic traceroute
traceroute 8.8.8.8

# Use ICMP instead of UDP (sometimes gets through firewalls that block UDP)
traceroute -I 8.8.8.8

# Traceroute to a hostname
traceroute google.com
```

**What the output tells you:**

- Each line is one router hop.
- Three latency values are shown (three probes per hop).
- `* * *` means the router does not respond to traceroute probes. This is common on internet routers and does not necessarily mean the path is broken. If later hops respond, the route is working.

**When to use `traceroute`:**

- A server is reachable but slow. Traceroute shows exactly which hop adds latency.
- Traffic is not arriving at the right destination.
- Debugging routing inside a VPC or between VPCs.

---

#### `netstat` and `ss` (Socket Statistics)

`ss` is the modern replacement for `netstat`. Both show active connections and listening sockets; use them to verify which services are listening on which ports. `netstat` still appears in older scripts and documentation, but `ss` is faster and is the preferred tool on current RHEL-family systems.

```bash
# Show all listening TCP sockets with process names
ss -tlnp

# Show all listening UDP sockets
ss -ulnp

# Show all established connections
ss -tnp

# Show connections on a specific port
ss -tnp | grep :22

# Show summary statistics
ss -s

# netstat equivalent, for reference
netstat -tlnp
```

**Major flags (both tools):**

- `-t`: TCP sockets
- `-u`: UDP sockets
- `-l`: listening sockets only
- `-n`: show numbers (do not resolve hostnames or port names)
- `-p`: show the process name and PID

**Reading the output of `ss -tlnp`:**

- `0.0.0.0:22` means sshd is listening on all interfaces on port 22.
- `127.0.0.1:3306` means MySQL is listening only on localhost and cannot be reached from outside the machine.
- The Process column shows exactly which process owns each socket.

> This is one of the first things you check when a service is not responding: is it actually listening on the expected port and interface?

#### `nslookup`

`nslookup` queries DNS servers to resolve hostnames to IP addresses or IP addresses to hostnames.

```bash
# Resolve a hostname to an IP
nslookup google.com

# Reverse lookup: IP to hostname
nslookup 8.8.8.8

# Query a specific DNS server (bypass your default resolver)
nslookup google.com 1.1.1.1

# Query for a specific record type
nslookup -type=MX google.com
nslookup -type=NS google.com
nslookup -type=TXT google.com
```

**What the output tells you:**

- `Server:` which DNS resolver your system used.
- `Non-authoritative answer:` the response came from a cache, not the authoritative name server.
- The resolved IP address.

> For more detailed DNS diagnostics, use `dig`.

---

#### `dig`

`dig` (Domain Information Groper) is the primary tool for detailed DNS diagnostics. It gives you full control over what you query and shows complete DNS responses, including TTL values, record types, and which server answered.

```bash
# Basic forward lookup
dig google.com

# Query for a specific record type
dig google.com A
dig google.com AAAA
dig google.com MX
dig google.com NS
dig google.com TXT
dig google.com CNAME

# Reverse lookup
dig -x 8.8.8.8

# Query a specific DNS server directly
dig @1.1.1.1 google.com A

# Short output (just the answer)
dig +short google.com A

# Trace the full DNS resolution path from root servers
dig +trace google.com
```

**Reading the output of `dig google.com A`:**

- `QUESTION SECTION:` the query you sent.
- `ANSWER SECTION:` the response.
- `Query time:` how long the DNS lookup took.
- `SERVER:` which DNS server answered.

| Field | Example Value | Meaning |
|---|---|---|
| status | `NOERROR` | Query succeeded |
| A record | `142.250.182.14` | IPv4 address for google.com |
| TTL | `122s` | Cached, expires in ~2 minutes |
| DNS server | `10.10.0.1` | Your local gateway/resolver |
| Query time | `9ms` | Fast, likely cached upstream |

> `dig +trace` is especially useful when DNS is behaving unexpectedly: it shows the full resolution chain from root servers through TLD servers to the authoritative name server.

### Part 4: Break Your Own DNS Deliberately

You are about to deliberately misconfigure DNS resolution on your own VM so you can practice diagnosing it. This is safe to do in a lab VM. Do not do this on a production system.

- Back up your current DNS configuration first
```bash
sudo cp /etc/resolv.conf /etc/resolv.conf.backup
```

- Point DNS resolution at a nonexistent, unreachable resolver
```bash
sudo bash -c 'cat > /etc/resolv.conf << EOF
nameserver 192.0.2.1
EOF'
```

`192.0.2.0/24` is a reserved address block specifically set aside for documentation and testing. It is guaranteed to never be a real, reachable host, which makes it perfect for this exercise.

If your system uses NetworkManager and tends to overwrite `/etc/resolv.conf` automatically, also run:

- Temporarily stop NetworkManager from regenerating the file
```bash
sudo nmcli connection modify "$(nmcli -t -f NAME connection show --active | head -1)" ipv4.dns "192.0.2.1"
sudo nmcli connection modify "$(nmcli -t -f NAME connection show --active | head -1)" ipv4.ignore-auto-dns yes
sudo systemctl restart NetworkManager
```

### Part 5: Diagnose the Broken Scenario

Now work through the same bottom-up sequence from the study note on the now-broken system. Run each command, capture the output, and write what it reveals.

**Step 1, Layer 3 check:**

```bash
ping -c 4 8.8.8.8
```

This should still succeed. You broke DNS, not basic IP connectivity. Write one sentence confirming Layer 3 is healthy and explaining why this result alone does not yet tell you anything is wrong.

**Step 2, name resolution check:**

```bash
ping -c 4 google.com
```

This should fail or hang, because `ping` cannot resolve the hostname to an IP address before it can even send the first packet. Write one sentence explaining specifically what this failure, combined with the success of Step 1, narrows the problem down to.

**Step 3, confirm with the dedicated DNS tools:**

```bash
nslookup google.com
```
```bash
dig google.com A
```

Both should report an error or simply time out, since they are trying to query a resolver at an address that does not exist. Capture the exact error message each tool produces.

**Step 4, query a different resolver directly to isolate the problem further:**

```bash
dig @8.8.8.8 google.com A
```

This bypasses your broken local configuration entirely and asks Google's resolver directly. It should succeed. Write two or three sentences explaining why this single command proves that the problem is specifically your local DNS configuration, and not a broader internet connectivity problem or a problem with Google's own DNS infrastructure.

**Step 5, cross-check with authoritative name server data:**

```bash
nslookup -type=NS github.com
```
```bash
dig @1.1.1.1 github.com A
```

Compare the answer from Cloudflare's resolver (`1.1.1.1`) to the answer you would normally get from your local resolver. If the answers differ once DNS is restored, explain why (different resolvers can return different cached records or use different anycast routing).

### Part 7: Diagnose a Routing Scenario

DNS is one category of failure. Routing is another. This part uses `traceroute` to diagnose a path problem rather than a name resolution problem.

- Trace the path to a real destination
```bash
traceroute 8.8.8.8
```
- Trace the path to your own default gateway
```bash
ip route show | grep default
```

Take the gateway address shown in that output and use it as the target for a second trace:

```bash
traceroute <paste the gateway address here>
```

Compare the two traces. The trace to your gateway should complete in a single hop. The trace to 8.8.8.8 should show several hops, and any `* * *` entries along the way should be read using the guidance in Part 2 rather than assumed to be a broken path.

Now examine your routing table directly:

```bash
ip route show
```

Write two or three sentences explaining, in your own words, what the default route line in this output means, and what would happen to all of your outbound traffic if that line were deleted.

### Common Issues

**`/etc/resolv.conf` keeps reverting on its own.** On systems using NetworkManager, the file is often regenerated automatically. Use the `nmcli ipv4.ignore-auto-dns yes` approach from Part 4 if a plain file edit does not stick.

**`ping 8.8.8.8` also fails, not just `ping google.com`.** This means you have a Layer 3 problem on top of, or instead of, the DNS problem you intended to create. Check `ip addr show` to confirm your VM still has a valid IP address, and check `ip route show` to confirm a default route still exists.

**`traceroute` shows nothing but asterisks for every hop.** Some networks and firewalls block the ICMP or UDP probes traceroute relies on. Try `traceroute -I 8.8.8.8` to switch to ICMP probes, which get through more firewalls than the default UDP probes.

**`ss` shows no output, or `netstat` is not found.** `ss` ships with the base system on Fedora/RHEL family distributions, so an empty result usually means no matching sockets exist rather than a missing tool. `netstat` is legacy and may need to be installed separately (`net-tools` package) if you specifically need it for a script or comparison.
