## 14. Networking

Understanding Linux networking is essential for a DevOps engineer. You need to be able to check connectivity, inspect network interfaces, troubleshoot DNS, examine open ports, and transfer files.

### Downloading Files

`curl` and `wget` are the two standard tools for downloading files and making HTTP requests from the terminal. Both are used constantly in DevOps work.

**`curl`: versatile HTTP client**

`curl` is used for both downloading files and interacting with APIs and web services.

Here's the list with real, working links:

---
* Download a file and save it with the same name
```bash
curl -O https://ftp.gnu.org/gnu/wget/wget-1.21.4.tar.gz
```
---
* Download and save with a custom name
```bash
curl -o wget-latest.tar.gz https://ftp.gnu.org/gnu/wget/wget-1.21.4.tar.gz
```
---
* Follow redirects (important for many download links)
```bash
curl -L https://github.com/git/git/archive/refs/tags/v2.45.0.tar.gz -O
```
---
* Test an HTTP endpoint and see the response code
```bash
curl -I https://httpbin.org/status/200
```
---
* Make a GET request and display output
```bash
curl https://api.github.com/zen
```
---
* Make a POST request with JSON data
```bash
curl -X POST -H "Content-Type: application/json" \
  -d '{"name":"test"}' https://httpbin.org/post
```
---
* Test with authentication
```bash
curl -u user:passwd https://httpbin.org/basic-auth/user/passwd
```
---
* Silent mode (no progress bar, useful in scripts)
```bash
curl -s https://httpbin.org/status/200
```
---
>Note:
>
>**httpbin.org**: Public service for testing HTTP requests; echoes back what you send.
>
>**api.github.com/zen**: Returns a short text string with `200 OK`, good for plain GET.
>
>**GitHub tarball URL**: Redirects to `codeload.github.com`, so `-L` is actually needed.
>
>**wget-1.21.4.tar.gz**: Real GNU FTP file (~5MB), works with `-O`/`-o`.
---
---
**`wget`: reliable file downloader**

`wget` is simpler than curl and better for downloading large files or mirroring websites.

---
* Download a file
```bash
wget https://ftp.gnu.org/gnu/wget/wget-1.21.4.tar.gz
```
---
* Download to a specific location
```bash
wget -O /tmp/wget.tar.gz https://ftp.gnu.org/gnu/wget/wget-1.21.4.tar.gz
```
---
* Download in the background
```bash
wget -b https://ftp.gnu.org/gnu/coreutils/coreutils-9.5.tar.gz
```
---
* Resume an interrupted download
```bash
wget -c https://ftp.gnu.org/gnu/coreutils/coreutils-9.5.tar.gz
```
---
> Note:
> 
> **wget-1.21.4.tar.gz**: Real GNU FTP file (~5MB), works with plain `wget` and `-O`.
>
> **coreutils-9.5.tar.gz**: Larger file (~7MB) from the GNU mirror, good for `-b` and `-c` since those matter more on bigger downloads.
---
> **`curl` vs `wget`**: Use `curl` when you need to interact with APIs or inspect HTTP headers. Use `wget` for straightforward file downloads, especially large ones or when you need to resume interrupted downloads.

### NetworkManager and `nmcli`: Making Configuration Persist

The `ip` command is the right tool for **inspecting** the network and for **temporary** changes. Anything you set with `ip addr add` or `ip route add` disappears at the next reboot, or as soon as NetworkManager decides to reapply its own profile. On every current Fedora, RHEL, CentOS Stream, and Rocky system, the component that actually owns the network state is **NetworkManager**, and the command line front end to it is `nmcli`.

The mental model is straightforward. NetworkManager stores **connection profiles**. A profile is a named set of settings (addressing method, IP address, gateway, DNS, autoconnect behaviour) that gets applied to a **device** (`enp0s3`, `eth0`, `wlan0`). A device can have several profiles defined, but only one active at a time. Configuration work therefore means editing a profile and then bringing it up, never poking at the interface directly.

Profiles are persisted as keyfiles in `/etc/NetworkManager/system-connections/`, one `.nmconnection` file per profile, in INI format. NetworkManager refuses to load a keyfile that is world readable, because these files can contain passwords, so they must be mode `600`.

---
* Show all connection profiles, whether active or not
```bash
nmcli connection show
```
---
* Show only the active profiles, with the device each one is bound to
```bash
nmcli connection show --active
```
---
* Show device status, which is the device oriented view rather than the profile oriented one
```bash
nmcli device status
```
---
* Show every setting inside one profile, which is what you read when a machine is behaving oddly
```bash
nmcli connection show "<profile_name>"
```
> Example:
```bash
nmcli connection show "enp0s3"
```
---

**Configuring a static IPv4 address.** This is the sequence used in Lab 2A. Four settings must be changed together: the address, the gateway, the DNS servers, and the method. Changing the address without changing `ipv4.method` from `auto` to `manual` leaves DHCP in charge and the static address will be ignored or duplicated.

* Set the address and prefix length
```bash
sudo nmcli connection modify "enp0s3" ipv4.addresses 192.168.56.20/24
```
* Set the default gateway
```bash
sudo nmcli connection modify "enp0s3" ipv4.gateway 192.168.56.1
```
* Set the DNS servers, space separated inside one quoted argument
```bash
sudo nmcli connection modify "enp0s3" ipv4.dns "192.168.56.1 1.1.1.1"
```
* Switch the profile from DHCP to static addressing
```bash
sudo nmcli connection modify "enp0s3" ipv4.method manual
```
* Make sure the profile comes up automatically at boot
```bash
sudo nmcli connection modify "enp0s3" connection.autoconnect yes
```
* Apply the change by cycling the profile
```bash
sudo nmcli connection down "enp0s3" && sudo nmcli connection up "enp0s3"
```
> Running these over SSH on the interface you are configuring will drop your session. Do this on the VM console, or on a second interface. This is the single most common way students lock themselves out of a lab VM.

> Set a gateway and DNS on a profile only if that network actually routes. On a host only adapter, which has no path to the internet, leave both unset and let the NAT adapter keep the default route. Two default gateways on one host produce a routing conflict that is tedious to diagnose. Lab 2A relies on this.
---
* Verify the result from the kernel's point of view, not NetworkManager's
```bash
ip addr show enp0s3
ip route show
resolvectl status
```
---

**Creating a profile from scratch**, which is what you do when Anaconda did not create one for the interface. Fedora 44 changed the installer so that it only writes profiles for devices you actually configured during installation, so a second NIC added later will often have no profile at all.

```bash
sudo nmcli connection add type ethernet con-name "static-lab" ifname enp0s8 \
  ipv4.method manual \
  ipv4.addresses 192.168.56.20/24 \
  ipv4.gateway 192.168.56.1 \
  ipv4.dns "1.1.1.1" \
  autoconnect yes
```
```bash
sudo nmcli connection up "static-lab"
```
---
* Inspect the keyfile that was just written, which is what the profile actually is on disk
```bash
sudo cat /etc/NetworkManager/system-connections/static-lab.nmconnection
```

A keyfile looks like this:

```ini
[connection]
id=static-lab
type=ethernet
interface-name=enp0s8
autoconnect=true

[ipv4]
method=manual
address1=192.168.56.20/24
gateway=192.168.56.1
dns=1.1.1.1;

[ipv6]
method=disabled
```

You may edit a keyfile by hand, but NetworkManager will not notice until you tell it to reread the directory:

```bash
sudo nmcli connection reload
sudo nmcli connection up "static-lab"
```

---
* Set the hostname through NetworkManager, which writes `/etc/hostname` and applies it immediately
```bash
sudo nmcli general hostname web01.lab.local
```
```bash
hostnamectl status
```
> `hostnamectl set-hostname` does the same job. Either is acceptable. Pick one and be consistent across your fleet.
---
* `nmtui` is the curses based front end to the same profiles. It is useful on a console when you are recovering a broken network and do not want to type long `nmcli` lines. It writes exactly the same keyfiles.
```bash
sudo nmtui
```
---

**A note on `/etc/sysconfig/network-scripts/`.** Older Red Hat documentation, and a great deal of older training material, tells you to write `ifcfg-eth0` files in that directory. Do not. The `ifcfg` format was deprecated in RHEL 9, and support for it has been removed entirely in RHEL 10 and its rebuilds. On a current system the directory is either empty or absent, and the only supported persistent format is the NetworkManager keyfile. If you inherit an older host with `ifcfg` files, convert them:

```bash
sudo nmcli connection migrate
```
