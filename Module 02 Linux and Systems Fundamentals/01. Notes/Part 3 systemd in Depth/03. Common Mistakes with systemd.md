## Common Mistakes with systemd

**Editing unit files in `/lib/systemd/system/` directly.** Package updates overwrite these files silently. Always use `systemctl edit <unit>` to create an override, or place a complete custom unit in `/etc/systemd/system/`.

**Forgetting `systemctl daemon-reload` after changing a unit file.** systemd caches unit files in memory. After editing a unit file, you must tell systemd to reload its configuration before restarting the service, or it will continue running the old version of the unit. The sequence is always: edit the file, then `daemon-reload`, then `restart` the unit.

**Using `systemctl stop` when you mean `systemctl disable`.** Stop halts the service right now but it will start again at the next boot. Disable removes it from the boot sequence so it never starts automatically again. If you want a service stopped permanently, you need both: `systemctl stop` followed by `systemctl disable`.

**Running applications as root in a service unit when a dedicated user works.** Any service running as root that has a security vulnerability can do anything on that machine. A service running as a dedicated, low privilege user is limited to exactly what that user is allowed to do. Every service unit you write should specify a `User=` and `Group=` directive unless there is a specific reason root access is genuinely required.

**Watching container logs instead of journald for containerized services managed by systemd.** When a container is managed by a systemd service unit (common with Podman's `podman generate systemd` output or with rootless containers on RHEL), the container's standard output and standard error both flow into journald. You can read them with `journalctl -u <container-service-name>` rather than needing `podman logs` or `docker logs` at all.
